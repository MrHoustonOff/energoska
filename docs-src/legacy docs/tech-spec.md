# Техническая спецификация — "Энергоська"

> Документ для ИИ-агентов и разработчика. Описывает технологический стек, инфраструктуру, деплой, и — самое критичное — исчерпывающие правила вёрстки и оптимизации под iOS Safari PWA. Все рекомендации по Safari/iOS проверены на актуальность на середину 2026 года (iOS 16.4–26).

---

## 1. Общий стек

| Слой | Технология | Комментарий |
|---|---|---|
| Backend | **FastAPI** (Python 3.12+) | Uvicorn как ASGI-сервер, за ним — Gunicorn как process manager с uvicorn workers, либо просто несколько процессов uvicorn под systemd (для нагрузки в 2 пользователя гарантированно достаточно) |
| ORM / миграции | **SQLAlchemy 2.x** + **Alembic** | Строгая типизация моделей, миграции коммитятся в репозиторий |
| БД | **PostgreSQL 16+** | Реляционная модель, JSON-поля не нужны |
| Очереди/фон | **APScheduler** (in-process) для MVP; при росте — Celery + Redis | Ежедневный курс валют, в будущем — еженедельный ML-агент статусов |
| Frontend | **React 18+ / TypeScript**, сборка через **Vite** | PWA-плагин `vite-plugin-pwa` (Workbox под капотом) |
| Стейт сервера | **TanStack Query (React Query)** | Кэш, инвалидация, фоновые рефетчи (важно для дуальных данных — партнёр обновил, я должен увидеть) |
| Стили | Tailwind CSS **или** CSS Modules — на усмотрение разработчика, но единый подход по всему проекту | Смотри также требования к производительности анимаций в разделе 4 |
| Графики | recharts / visx | Лёгкие, декларативные, достаточно для линий/радаров/гистограмм |
| Push | Web Push API + VAPID, библиотека **pywebpush** на бэкенде | Подробности — раздел 5 |
| Обработка фото | Отдельный **Go**-микросервис (BiRefNet_HR), pull-модель к очереди задач | Уже описано в основной спецификации продукта |
| Веб-сервер / реверс-прокси | **Nginx** | TLS-терминация, отдача статики фронта, проксирование `/api` на FastAPI |
| TLS | **Let's Encrypt / certbot** | HTTPS обязателен — без него не заработает ни Service Worker, ни Web Push |
| ОС сервера | **Ubuntu Server 24.04 LTS** | Прод |
| Контейнеризация | **Docker + docker-compose** — целевая архитектура на будущее (см. раздел 3.4). Сейчас разработка идёт без Docker, локально | Важно закладывать конфиги сразу, чтобы переезд был безболезненным |

## 2. Локальная разработка (без Docker, текущий этап)

### 2.1 Backend
```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```
- `.env` файл (в `.gitignore`) — переменные: `DATABASE_URL`, `JWT_SECRET`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `EXCHANGE_RATE_API_KEY`, `PHOTO_WORKER_API_KEY`.
- PostgreSQL ставится нативно на машину разработчика (или через `docker run postgres` — единственное разумное исключение из "без докера", т.к. поднять локальную БД руками неудобно и бессмысленно).
- Alembic-миграции — прогонять при каждом изменении моделей: `alembic revision --autogenerate -m "описание"` → `alembic upgrade head`.

### 2.2 Frontend
```bash
npm create vite@latest frontend -- --template react-ts
npm install
npm run dev
```
- Vite dev-сервер проксирует `/api/*` на `http://localhost:8000` (настройка в `vite.config.ts`, секция `server.proxy`).

### 2.3 КРИТИЧЕСКИ ВАЖНО: HTTPS даже в локальной разработке
Service Worker, Push API и `manifest.json`-фичи в Safari **не работают без HTTPS** (единственное исключение — `localhost`, но `localhost` не позволяет тестировать на реальном iPhone в локальной сети). Для тестирования PWA-функций на настоящем айфоне в процессе разработки — обязательно поднять локальный HTTPS:
- Использовать **mkcert** для генерации локального доверенного сертификата.
- Либо сразу тестировать на staging-поддомене реального сервера (например, `dev.energiska.example.com`) с настоящим Let's Encrypt сертификатом — это надёжнее и рекомендуется как основной способ проверки PWA-функционала на протяжении всей разработки.

**Практическое правило: любую PWA/Safari-специфичную фичу (манифест, установка на экран, push, safe-area) тестируем ТОЛЬКО на реальном iPhone через "Добавить на экран Домой", никогда через симулятор или обычную вкладку браузера.** Псевдо-PWA поведение в обычной вкладке Safari принципиально отличается от установленного standalone-приложения.

## 3. Продакшн-инфраструктура

### 3.1 Схема
```
Интернет ──HTTPS──► Nginx (443) ──► ┌─ статика фронта (React build, /var/www/energiska)
                                     └─ /api/* ──proxy_pass──► Uvicorn (127.0.0.1:8000, FastAPI)
                                                                     │
                                                                PostgreSQL (127.0.0.1:5432)
```
Go-воркер обработки фото живёт **не на сервере**, а на домашнем компьютере пользователя — он сам стучится на публичный эндпоинт очереди задач через HTTPS, авторизуясь статическим API-ключом.

### 3.2 Nginx — ключевые моменты конфига
- Редирект с `80` на `443` (HTTP → HTTPS обязателен, PWA не заработает на HTTP).
- `gzip` **и** `brotli` компрессия для текстовых ответов (JS/CSS/HTML/JSON) — критично для скорости на мобильной сети.
- Правильные `Cache-Control` заголовки:
  - Хэшированные бандлы фронта (Vite добавляет хэш в имя файла) — `Cache-Control: public, max-age=31536000, immutable`.
  - `index.html` и `manifest.json` — `Cache-Control: no-cache` (чтобы обновления PWA подхватывались, а не залипали в кэше устройства).
  - `service-worker.js` — **обязательно** `Cache-Control: no-cache` (иначе обновления приложения не будут доходить до пользователя неделями — классическая ошибка PWA).
- `client_max_body_size` — увеличить под загрузку фото (например, `10m`).

### 3.3 Systemd
- Backend как systemd-сервис (`energiska-api.service`), `Restart=always`, запуск через `uvicorn` (можно с несколькими воркерами через `--workers 2`, для текущей нагрузки достаточно).
- Автозапуск при перезагрузке сервера (`systemctl enable`).
- Логи — через `journalctl`, ротация стандартная через journald (для двух пользователей полноценный стек мониторинга — избыточен).

### 3.4 Docker — целевая архитектура (готовим заранее, переезд без Docker → с Docker должен быть тривиальным)
```yaml
# docker-compose.yml (ориентир на будущее)
services:
  postgres:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]
    env_file: .env
  api:
    build: ./backend
    depends_on: [postgres]
    env_file: .env
    restart: always
  frontend:
    build: ./frontend      # multi-stage: сборка Vite → отдача через nginx
    restart: always
  nginx:
    image: nginx:alpine
    ports: ["80:80", "443:443"]
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf
      - ./certbot/conf:/etc/letsencrypt
    depends_on: [api, frontend]
volumes:
  pgdata:
```
- Backend Dockerfile — многостадийная сборка, финальный образ на `python:3.12-slim`.
- Frontend Dockerfile — стадия сборки (`node:20-alpine`, `npm run build`) → стадия отдачи (`nginx:alpine`, копируем `dist/`).
- Уже сейчас (даже без Docker) держим переменные окружения через `.env` и конфиги без хардкода путей — это и есть та самая "подготовка к переезду".
- Резервное копирование БД: cron-задача `pg_dump` раз в сутки + хранение бэкапов вне сервера (например, синхронизация в облако или на второй диск) — учитывая требование "максимально долгое хранение" данных.

## 4. Производительность GUI (общие принципы, не только iOS)

1. **Code splitting** — роуты грузятся лениво (`React.lazy` + `Suspense`), не тащим весь бандл сразу на логин.
2. **Виртуализация списков** — если список энергетиков вырастет (а он будет расти — "кто угодно может создавать энергосы"), использовать `react-virtual`/`react-window` для сетки карточек, чтобы не рендерить сотни DOM-узлов разом.
3. **Изображения**:
   - Формат **WebP/AVIF** для фото энергетиков (после обработки BiRefNet отдаём в оптимизированном формате).
   - `loading="lazy"` на все изображения вне первого экрана.
   - Явно задавать `width`/`height` (или `aspect-ratio` в CSS) — избегаем layout shift при подгрузке.
4. **Мемоизация**: `React.memo` на карточках списка, `useMemo`/`useCallback` там, где пересчёт/пересоздание функций реально дорого (не злоупотреблять — не оборачивать вообще всё подряд, это тоже стоит ресурсов).
5. **Сеть**: React Query с разумным `staleTime` — не дёргаем бэкенд на каждый ре-рендер, но инвалидация при мутациях (например, после "Выпить") должна быть точечной, а не полным сбросом кэша.
6. **Бандл**: анализировать размер сборки (`vite-bundle-visualizer` или аналог), не тащить тяжёлые библиотеки целиком (например, импортировать конкретные функции lodash, а не весь пакет).
7. **Шрифты**: `font-display: swap`, подключать только реально используемые начертания, предпочтительно системный шрифтовой стек (`-apple-system, BlinkMacSystemFont, ...`) — это ещё и часть "нативного" ощущения на iOS.

## 5. iOS Safari PWA — исчерпывающий гайд

Это самый критичный раздел. Ниже — обязательные к исполнению правила. Отступление от них ломает либо установку, либо push, либо ощущение "нативности".

### 5.1 Манифест (`manifest.json`)
Обязательные поля:
```json
{
  "name": "Энергоська",
  "short_name": "Энергоська",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#0B0B0F",
  "theme_color": "#0B0B0F",
  "orientation": "portrait",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icons/icon-512-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}
```
- `display: "standalone"` — обязательно, иначе приложение откроется как вкладка Safari (а без standalone-режима **Push вообще не будет работать**, см. раздел 5.5).
- Полный набор иконок (минимум 192×192 и 512×512, плюс maskable-вариант) — сгенерировать один раз через любой PWA icon generator и закоммитить в репозиторий.

### 5.2 HTML `<head>` — мета-теги, специфичные для iOS
Safari **игнорирует** часть манифеста и требует собственные Apple-специфичные теги — их нужно указывать **в дополнение** к манифесту, а не вместо него:

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover" />
<meta name="apple-mobile-web-app-capable" content="yes" />
<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent" />
<meta name="apple-mobile-web-app-title" content="Энергоська" />
<link rel="apple-touch-icon" href="/icons/icon-192.png" />
<link rel="apple-touch-startup-image" href="/splash/iphone-splash.png" />
```
- **`viewport-fit=cover`** — критично: без него контент не будет доходить до краёв экрана на iPhone с "чёлкой"/Dynamic Island, появятся некрасивые белые/чёрные полосы.
- `apple-mobile-web-app-status-bar-style: black-translucent` — статус-бар становится прозрачным и накладывается на контент (в сочетании с safe-area-inset ниже — это то самое "нативное" ощущение).
- Splash-скрины (`apple-touch-startup-image`) — Apple требует свою картинку под каждое разрешение экрана для показа при запуске приложения (белый экран при холодном старте иначе смотрится дёшево). Сгенерировать набор под актуальные размеры iPhone/iPad через генератор (например, `pwa-asset-generator`).
- Примечание на будущее: начиная с iOS 26 сайты, добавленные на домашний экран, по умолчанию открываются как standalone-приложение даже без части этих тегов — но **не полагаемся на это как на единственный источник поведения**, полный набор тегов обязателен для консистентности на диапазоне iOS 16.4–26+, которым реально пользуются люди.

### 5.3 Safe Area (вырезы, Dynamic Island, home indicator)
Каждый экран, содержащий контент у самого верха/низа (шапки, нижние панели навигации, плавающие кнопки), обязан учитывать безопасные зоны через CSS-переменные:

```css
.app-header {
  padding-top: env(safe-area-inset-top);
}
.bottom-nav {
  padding-bottom: env(safe-area-inset-bottom);
}
.fab-button {
  bottom: calc(16px + env(safe-area-inset-bottom));
}
```
**Правило**: любой фиксированный по позиции элемент (`position: fixed` / `sticky`, прижатый к краю экрана) обязан иметь соответствующий `env(safe-area-inset-*)` в отступах. Без этого кнопки будут заезжать под home-indicator или под вырез камеры.

### 5.4 Вьюпорт, `100vh`, и "прыгающая" клавиатура — САМАЯ частая причина сломанного UX на iOS

Это отдельный класс проблем, который системно ломает PWA на iOS, если не заложить архитектуру экрана правильно **с самого начала**.

**Проблема 1 — классическая "ложь про 100vh".** На iOS `100vh` считается от полной высоты экрана, включая области, перекрытые адресной строкой/тулбаром Safari, из-за чего низ страницы обрезается или появляется лишний скролл.
**Решение:** никогда не использовать `100vh` для полноэкранных контейнеров. Использовать **`100dvh`** (dynamic viewport height) — современный CSS-юнит, который корректно учитывает реальную видимую область, включая изменения при появлении клавиатуры.

**Проблема 2 — при открытии клавиатуры в установленной (standalone) PWA видимая область "усыхает" и не восстанавливается до конца сессии.** Это известный баг WebKit в standalone-режиме: после первого открытия клавиатуры `visualViewport.height`/`100dvh` могут "залипнуть" на уменьшенном значении даже после закрытия клавиатуры, пока приложение не перезапущено.
**Решение (обязательный паттерн верстки экрана):**
1. Строим "shell" приложения как жёсткую флекс-структуру, а не через абсолютные `vh`-высоты каждого блока:
   ```css
   html, body, #root {
     height: 100dvh;
     overflow: hidden; /* блокируем "резиновый" скролл всей страницы */
   }
   .app-shell {
     display: flex;
     flex-direction: column;
     height: 100%;
   }
   .app-header, .app-bottom-nav {
     flex: none; /* фиксированная высота, не через position:fixed привязанный к vh */
   }
   .app-scroll-area {
     flex: 1 1 auto;
     overflow-y: auto;
     overscroll-behavior: contain;
     -webkit-overflow-scrolling: touch;
   }
   ```
   Использование `flex: 1` для скроллируемой зоны вместо фиксированной высоты в `vh` — сама зона "сжимается" вместе с клавиатурой естественным образом, без ручных пересчётов.
2. Хедер и нижняя навигация — **не** `position: fixed` относительно вьюпорта, а часть flex-раскладки (`flex: none`). Это устраняет главный источник "прыгающих" и "уезжающих" панелей при появлении клавиатуры — им физически некуда "уезжать", раз они не привязаны к позиции окна, а являются частью потока.
3. Если после закрытия клавиатуры видимая область всё равно осталась "усохшей" (баг WebKit) — принудительно форсировать пересчёт вьюпорта на `blur` инпута: временно переключить CSS-класс корневого контейнера (`display: none` → `flex` на следующий тик через `requestAnimationFrame`), что заставляет WebKit заново измерить viewport. Это должно быть реализовано как общий хук (`useIOSViewportFix`), применяемый один раз на уровне `app-shell`, а не точечно на каждом экране.
4. Модалки (в первую очередь модалка "Выпить" с формой) — при фокусе на инпут внутри модалки категорически **не** позиционировать модалку через `position: fixed` + `top/bottom` в связке с `vh`. Модалка должна следовать тому же flex-паттерну shell'а: `max-height: 90dvh`, внутренний `overflow-y: auto` на контентную зону, кнопка "Сохранить" — как `flex: none` футер модалки, а не `position: sticky` от вьюпорта.

**Проблема 3 — автоматический зум при фокусе на инпут.** Safari на iOS автоматически зумит страницу, если у сфокусированного `<input>`/`<textarea>`/`<select>` размер шрифта меньше 16px — выглядит очень "неродно" и дёргано.
**Решение:** для всех полей ввода **обязательно** `font-size: 16px` или больше (можно визуально компенсировать через `transform: scale()`, если дизайну нужен визуально меньший текст, но реальный `font-size` в CSS должен быть ≥16px).

### 5.5 Инпуты и клавиатура — устранение "лагов"
- На каждом `<input>` задавать корректный `inputmode` (`inputmode="decimal"` для слайдеров/цены при текстовом вводе, `inputmode="numeric"` для чисел, `inputmode="text"` по умолчанию) и `enterkeyhint` (`"done"`, `"search"`, `"next"`) — это меняет раскладку системной клавиатуры под контекст и ускоряет ввод, ощущается как нативное поведение.
- Не вешать тяжёлую логику (валидация, сетевые запросы) синхронно на каждое нажатие клавиши — обязательно **debounce** (150–300мс) для полей, вызывающих сетевые операции (например, поиск по нику при приглашении партнёра, autocomplete тегов/брендов).
- Слайдеры оценки (0–10, шаг 0.5) — реализовывать на нативном `<input type="range">` с кастомизацией через CSS (`::-webkit-slider-thumb` и т.п.), а не через полностью самописный drag-компонент на `pointermove`. Нативный range-input на iOS уже оптимизирован под touch и не будет "лагать"; самописная реализация через JS-обработчики частo подтормаживает при частых перерисовках (особенно если на каждый пиксель перерисовывается легенда/число).
- Если критично важна кастомная визуальная стилизация слайдера (акцентная метка прошлого значения поверх трека, как описано в продуктовой спецификации) — эта метка рисуется как **отдельный абсолютно позиционированный элемент поверх нативного range-инпута**, а не как часть его перерисовки на каждое движение пальца. Обновление позиции метки — через CSS custom property (`--mark-position`), обновляемую вне React re-render цикла (прямое обращение к DOM/`ref`), чтобы не гонять весь компонент через React на каждый пиксель перетаскивания.
- Все интерактивные элементы — `touch-action: manipulation` в CSS, чтобы убрать 300мс задержку тапа и предотвратить случайный двойной-тап-зум.

### 5.6 Скролл и анимации — ощущение "родного" приложения
- `overscroll-behavior: contain` на всех скроллируемых контейнерах — предотвращает "протекание" скролла на родительские элементы (классическая проблема модалок поверх страницы).
- Анимации переходов/появлений — **только** через `transform` и `opacity` (GPU-композиция), никогда через анимацию `width`/`height`/`top`/`left`/`margin` (вызывает layout/reflow на каждый кадр — источник "лагающего" ощущения).
- `will-change: transform` — точечно, только на реально анимируемых элементах, и снимать после завершения анимации (постоянный `will-change` на многих элементах ест память и может, наоборот, замедлить рендер).
- Библиотека для сложных переходов между экранами — Framer Motion (использует `transform`/`opacity` под капотом), но не обязательна — CSS-transitions вполне достаточно для карточек/модалок.
- Списки/сетки — `content-visibility: auto` на офскрин-карточках может ускорить первичный рендер длинных списков (поддержка в Safari — проверить актуальность на момент реализации, т.к. это относительно новый CSS-примитив).

### 5.7 Тестовый чек-лист перед каждым релизом (обязателен для ИИ-агента при реализации фич)
Перед тем как считать любую страницу с формами/списками/модалками готовой, обязательно проверить на реальном iPhone (в установленной как PWA версии, не в браузере):
- [ ] Нет белых/чёрных полос сверху/снизу при повороте/открытии на устройстве с вырезом.
- [ ] При фокусе на любой инпут — нет автозума страницы.
- [ ] При открытии/закрытии клавиатуры — хедер и нижняя навигация не "прыгают" и не съезжают.
- [ ] После закрытия клавиатуры — вью возвращается к полной высоте (нет "усохшего" экрана до конца сессии).
- [ ] Скролл внутри модалки не протекает на фон.
- [ ] Кнопки внизу экрана не перекрыты индикатором Home.
- [ ] Слайдеры оценки двигаются плавно без визуальных "скачков"/дропа кадров при быстром свайпе.

## 6. Web Push — реализация

### 6.1 Требования (обязательны все одновременно)
- iOS/iPadOS **16.4+**.
- Сайт обслуживается по **HTTPS**.
- Корректный `manifest.json` с `display: standalone`.
- **PWA должна быть установлена на домашний экран** — Push API физически недоступен в обычной вкладке Safari, независимо от браузера (даже Chrome/Edge на iOS используют WebKit и подчиняются тому же ограничению).
- Запрос разрешения на уведомления возможен только **после явного действия пользователя** (тап по кнопке) — нельзя запрашивать permission автоматически при загрузке.

### 6.2 Обнаружение режима запуска
Перед показом любого UI, связанного с push, проверяем, что приложение запущено именно как установленное standalone-приложение:
```js
const isStandalone =
  window.matchMedia('(display-mode: standalone)').matches ||
  window.navigator.standalone === true; // легаси-флаг для iOS
```
Если `isStandalone === false` — вместо кнопки "Включить уведомления" показываем инструкцию "Добавьте приложение на экран Домой через Поделиться → На экран «Домой»", в идеале с иллюстрацией/скриншотом шагов (поскольку доля пользователей, самостоятельно находящих эту функцию, крайне низкая — но у нас ровно два целевых пользователя, которым можно объяснить голосом один раз, так что сложную обучающую анимацию можно не делать).

### 6.3 Флоу подписки (двухшаговый промпт)
Safari требует, чтобы разрешение запрашивалось не "в лоб" системным промптом сразу — рекомендуемая практика (и фактически обязательная для приемлемого UX, раз системный промпт можно показать лишь один раз и повторно только через настройки iOS):
1. Кастомный экран/баннер внутри приложения: "Хочешь получать уведомления, когда партнёр отметился энергосом? [Включить]".
2. По тапу — вызывается `Notification.requestPermission()`, показывающий уже системный iOS-промпт.
3. При согласии — `registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: VAPID_PUBLIC_KEY })`, полученный объект подписки (`endpoint`, `keys.p256dh`, `keys.auth`) отправляется на бэкенд и сохраняется в таблице `push_subscriptions` (привязана к `user_id`).

### 6.4 Backend
- Генерация пары VAPID-ключей один раз (`pywebpush` или `web-push` CLI), приватный ключ — только в `.env` на сервере.
- Эндпоинт `POST /push/subscribe` — сохраняет/обновляет подписку пользователя.
- Отправка: при триггере события (см. три сценария в продуктовой спецификации) — сервер вызывает `pywebpush.webpush(subscription_info=..., data=json.dumps(payload), vapid_private_key=..., vapid_claims={"sub": "mailto:you@example.com"})`.
- Обрабатывать `410 Gone`/`404` ответы от push-сервиса — значит подписка протухла (пользователь удалил приложение/отозвал разрешение), удалять такую запись из БД.
- **Важно закладывать нестабильность**: по опыту разработчиков, доставка iOS web push иногда перестаёт работать спустя время без явной причины (известная особенность платформы, не баг вашего кода) — не полагаться на push как единственный канал критичной информации, это дополнительный приятный бонус поверх ленты событий в самом приложении.

### 6.5 Service Worker — обработка push-события
```js
self.addEventListener('push', (event) => {
  const data = event.data.json();
  event.waitUntil(
    self.registration.showNotification(data.title, {
      body: data.body,
      icon: '/icons/icon-192.png',
      badge: '/icons/badge-72.png',
    })
  );
});

self.addEventListener('notificationclick', (event) => {
  event.notification.close();
  event.waitUntil(clients.openWindow(data.url || '/'));
});
```
- На перспективу: Safari 18.4+ поддерживает **Declarative Web Push** (сервер сразу присылает готовый JSON пейлоад уведомления, без выполнения кода Service Worker для отображения) — это более новый и надёжный механизм, но экосистема инструментов вокруг него ещё формируется на момент написания документа. **Рекомендация**: на MVP реализовать классический (императивный) Web Push через `pywebpush`, как описано выше — он гарантированно работает на всём диапазоне iOS 16.4+. Переход/добавление поддержки Declarative Web Push — опциональное улучшение уже после MVP, когда экосистема (библиотеки, документация) созреет.

## 7. Безопасность (минимально необходимое для MVP, но не менее)
- HTTPS everywhere — без исключений.
- Пароли — только хэш (argon2id), никогда в открытом виде ни в БД, ни в логах.
- JWT access-токен с коротким TTL + httpOnly refresh cookie (`Secure`, `SameSite=Lax` или `Strict`).
- CORS — ограничить origin только своим доменом фронта.
- Rate limiting на `/auth/*` эндпоинты (например, через nginx `limit_req`) — от брутфорса пароля, даже при двух пользователях это дешёвая защита.
- Валидация загружаемых файлов (фото) — проверка MIME-типа и размера на бэкенде, не доверять расширению файла.
- API-ключ Go-воркера фото — отдельный секрет, не пересекающийся с пользовательской аутентификацией, с возможностью ротации.

## 8. Резюме приоритетов для ИИ-агента при реализации

Если нужно расставить приоритеты при разработке (что нельзя упрощать/пропускать):
1. **HTTPS + корректный манифест + safe-area с самого первого экрана** — без этого всё остальное бессмысленно тестировать на iPhone.
2. **Flex-based app-shell с `100dvh`**, а не россыпь `vh`-хаков по компонентам — закладывается один раз в самом начале, переделывать через полгода будет больно.
3. **`font-size: 16px+` на всех инпутах** — тривиально, но именно это чаще всего забывают, и это самый заметный "неродной" баг.
4. Push — реализуется после того, как базовый CRUD и PWA-оболочка стабильны, не раньше (иначе будет сложно отличить баги push от базовых архитектурных проблем).
