# Энергоська: старт для агента

> **ПРОТОКОЛ РАБОТЫ. Выполняй дословно, по порядку. Это важнее любых твоих соображений об удобстве.**
> Контекст: токены ограничены, поэтому каждая ошибка дорога. Результат строго ревьюит Claude (код, контракт, правила) и ещё строже владелец (дизайн, пиксель в пиксель). Сдача «примерно» отклоняется и переделывается.
>
> **ГЛАВНОЕ ПРАВИЛО: ПО ОДНОМУ ЭКРАНУ, С ОСТАНОВКОЙ НА ПРОВЕРКУ ВЛАДЕЛЬЦА.** Блок из нескольких экранов делать НЕЛЬЗЯ одним заходом. Порядок:
> 1. Сначала (до кода) напиши владельцу список экранов блока в порядке работы и дождись «ок».
> 2. Бери ОДИН экран. Выполни для него шаги 1–4 ниже. Закоммить (`feat: <экран>`), запушь, ответь по шаблону шага 5 (коротко, с путями эталона для сверки).
> 3. **ОСТАНОВИСЬ. Не начинай следующий экран**, пока владелец не напишет «принято» (или не пришлёт замечания). Замечания исправляй на ЭТОМ же экране, снова запушь и снова остановись.
> 4. Только после «принято» бери следующий экран. Общие компоненты (карточка, кнопка и т.п.) создавай при первом экране, который их использует, и дальше переиспользуй, а не переделывай.
> 5. Первый экран блока самый важный: на нём владелец задаёт планку. Если он отклонён дважды, остановись и спроси, что именно не так, вместо третьей попытки вслепую.
>

> 1. `git fetch origin && git checkout main && git pull`; создай/используй ветку, заданную средой (`claude/...` или `task/<имя>`); все коммиты только в неё. В `main` не пушить, PR не создавать.

> 3. Прочитай (и только это): `STATE.md` (своя задача), этот файл целиком, `docs-src/docs/12-demo-data.md`, нужный диапазон `app-ux.md` по `app-ux.INDEX.md`, `README.md` и `preview.html` эталонных компонентов. `app-ux.md` и Библию целиком не читать.
>
> **ШАГ 1. Эталон.** Сними скриншоты эталона `preview.html` (390×844, тёмная и светлая тема). Если нет инструмента для скриншотов, скажи об этом СРАЗУ в сообщении владельцу и не продолжай вслепую. Перепиши для себя список элементов эталона: каждая надпись, иконка, отступ, цвет (токены), радиус, шрифт и размер.
>
> **ШАГ 2. Данные.** Экран берёт данные только через `src/api` (`api.drinks`, `api.intakes`, ...). Если данных не хватает: сначала дополни `api/openapi.yaml` + `npm run api:types` + мок + демо-генератор (`src/api/mock/demo/`) + тест, и перечисли это в отчёте. Данных в разметке нет, текстов от себя нет.
>
> **ШАГ 3. Вёрстка.** Копируй структуру и стили эталона и `docs-src/reference/energoska.css`; цвета/радиусы/шрифты только токенами `docs-src/tokens/tokens.css`. Один компонент = один файл ≤ 300 строк, одна ответственность. Анимируются только `transform` и `opacity`. Состояния: обычное, пусто, загрузка (скелетон тех же размеров), ошибка, нет сети, лимит 2 банки (где есть), светлая тема, «с клавиатурой» (где есть поле).
>
> **ШАГ 4. Самопроверка (обязательна, выполняй команды).** Всё должно быть пусто/OK:
> - `npm run check && npm test && npm run build`
> - Регистр имён: `git ls-files | tr 'A-Z' 'a-z' | sort | uniq -d` (должно быть пусто).
> - Замороженное не тронуто: `git diff --stat origin/main -- src/viewport.js index.html` (пусто; `src/styles.css` и `Shell.svelte` только в пределах, разрешённых в `STATE.md`).
> - Размер файлов: `find src -name '*.svelte' -o -name '*.ts' -o -name '*.css' | xargs wc -l | sort -rn | head` (нет файла > 300 строк в твоих правках).
> - Лишние цвета: `grep -rnE "#[0-9a-fA-F]{3,8}" src --include=*.svelte --include=*.css` в твоих файлах (цвета только из токенов; допустимо в `src/api/mock/demo`).
> - Демо: `grep -rn MOCK-DEMO src` не вырос без причины; в разметке нет демо-значений.
> - Скриншоты твоего экрана (390×844, обе темы) положи РЯДОМ с эталонными, сравни глазами элемент за элементом, исправь расхождения, повтори. Пары «эталон | моё» сохрани в `docs-src/reports/<задача>/` (png).
>
> **ШАГ 5. Сдача ОДНОГО экрана.** Обнови `STATE.md` (что сделано, что дальше), закоммить по-русски (`feat:`, `fix:`, `refactor:`, `docs:`), `git push -u origin <ветка>`. Затем ответь владельцу ОДНИМ коротким сообщением по шаблону:
> 1. Ветка и последний коммит.
> 2. Что сделано (3–6 строк).
> 3. Результаты команд шага 4 (одной строкой: check / test / build / регистр / заморозка).
> 4. Отступления от эталона (список, с причиной) и вопросы владельцу.
> 5. «Не проверено на устройстве»: что именно смотреть на iPhone (клавиатура, safe-area, плавность, автозаполнение, push).
> 6. «Что открыть владельцу для сверки»: список эталонов путями относительно `docs-src\components\` (например `ScreenCatalog\preview.html`, рядом `dark.webp` и `light.webp`) и в каком разделе приложения смотреть каждый экран (вкладка → экран → как вызвать состояние, включая профиль демо из Лаборатории).
>
> **СТОП-правила (не гадай, спроси в отчёте и продолжи остальным):** нужна правка замороженного; не хватает данных/поля в контракте и непонятно как; в эталоне есть то, чего нет в спецификации (и наоборот); тест падает по причине, не связанной с твоей задачей.
> **ЗАПРЕТЫ:** выдуманные тексты и подсказки, тосты, свои демо-данные вне `src/api/mock/demo/`, новые цвета/шрифты/тени, пропуск состояний, «потом доделаем», отключение или удаление тестов, правки чужих блоков «заодно», обход заморозки, `any` без причины, `localStorage` в экранах, имена файлов, различающиеся только регистром.

Мобильное PWA для iOS Safari (пара оценивает энергетики, максимум 2 банки в день). Идёт этап **законченного фронтенда** на моках; бэкенд позже.

## Читай по порядку (и только это; остальное по необходимости)
1. `STATE.md`: что готово, что делать сейчас, правила процесса.
2. `docs-src/AGENTS.md`: нерушимые правила продукта, визуального языка и техники.

**Не читай целиком**: `app-ux.md` (114 КБ), `SAFARI_PWA_BIBLE.md` (51 КБ). Библия нужна только если трогаешь каркас или платформенное поведение.

**Стек:** Svelte 5 + TypeScript + Vite (`npm run dev`, `npm run check`, `npm run build`).

## Как работать
- Одна задача = одна ветка `task/<имя>`; коммиты по-русски (`feat:`, `fix:`, `refactor:`, `docs:`); **push обязателен**: владелец смотрит результат через `git pull` на компьютере и проверяет на iPhone.
- **PR не создавать и в `main` не пушить без просьбы владельца.** Владелец сам скажет, когда вливать.
- Меняй ровно то, о чём просят. «Не сломай остальное» действует всегда.
- Новый экран: найди 1–2 ближайших эталона в `docs-src/components/INDEX.md`, возьми токены из `docs-src/tokens/tokens.css`, опиши все состояния (пусто, загрузка, ошибка, нет сети, лимит 2 банки, светлая тема, «с клавиатурой»).
- Всё, что нельзя проверить без телефона (safe-area, клавиатура, push, плавность), прямо пиши как «не проверено на устройстве».
- В конце сессии: обнови `STATE.md` (что сделано, что дальше), закоммить, запушь.

## ГЛАВНОЕ ТРЕБОВАНИЕ К ВНЕШНЕМУ ВИДУ: пиксель в пиксель с эталоном
Экран должен выглядеть **как `preview.html` компонента, один в один**: размеры, отступы, радиусы, шрифты, цвета, тени, зерно, иконки, тексты. «Похоже» и «в духе» не принимается. Порядок: открой `preview.html`, сними скриншот эталона (Playwright, 390×844, тёмная и светлая тема), сделай экран, сними свой скриншот и **сравни рядом**; расхождения исправь до сдачи. Стили бери копированием из эталона и `reference/energoska.css`, значения только из токенов; не пересобирай вёрстку «по смыслу». Любое отступление от эталона перечисли в отчёте с причиной. В отчёт приложи пары скриншотов «эталон / моё».

## ДЕМО-ДАННЫЕ из макета (обязательно)
**Каркас демо УЖЕ СДЕЛАН и подключён: прочитай `docs-src/docs/12-demo-data.md`** (профили, как расширять, как удалить). После `npm run dev` вход уже выполнен (admin / admin), в моке пара, банки, оценки, записи, вода; переключатель состояний: Ещё → Лаборатория → «Демо-данные». Не создавай свои демо-данные, расширяй `src/api/mock/demo/`. Ниже правила, которым это подчиняется.
Наполнение экрана берём **из макета `preview.html`**: те же имена, банки, оценки, цены, ленту, фото. Это пример заполнения (плейсхолдер), но он должен быть встроен правильно, через мок `src/api`, а не вшит в разметку. И так, чтобы **удалить одним действием**:
- все демо-данные лежат ТОЛЬКО в `src/api/mock/demo/` (один каталог) и подключаются одной строкой/флагом в `src/api/mock/seed.ts`;
- каждое место, где демо влияет на код, помечено комментарием `MOCK-DEMO` (`// MOCK-DEMO: ...` или `<!-- MOCK-DEMO -->`), чтобы `grep -rn MOCK-DEMO src` показывал всё;
- в UI нет ни одного захардкоженного демо-значения; экран получает данные только через `api`, а при пустых данных показывает состояние «пусто» из спецификации;
- в отчёте напиши, как удалить демо: «удалить каталог X и строку Y».
Контракт и мок остаются: демо-данные лишь заполняют их.

## Уроки T0–T2 (обязательно)
- **Владелец на Windows/macOS: имена файлов не должны различаться только регистром** (`Toast.svelte` и `toast.svelte.ts` ломали `npm run dev`). Модуль состояния называй иначе (`toastState.svelte.ts`).
- **Не добавляй того, о чём не просили**: поясняющие тексты в интерфейсе («iPhone предложит сохранить пароль…»), тосты, трюки с системными окнами. Тексты берём из спецификации, лишнего не придумываем. Владелец убирал такое трижды.
- **Тостов в приложении нет**, кроме `NotificationToasts` из спецификации (§9.4). Результат действия показывай на самом экране.
- Корень приложения: `src/App.svelte` выбирает `Splash` / `AuthGate` / `Shell.svelte`. DOM `Shell.svelte` (шапка, список, панель вкладок) заморожен как каркас; исключение: в T3 владелец разрешил переделать ВНЕШНИЙ ВИД панели вкладок (см. `STATE.md`), поведение при клавиатуре и `viewport.js` по-прежнему нельзя трогать. Фон и зерно: `src/surface.css`, `src/Backdrop.svelte`; шапка прозрачная. Эти правки ещё ждут полной проверки чек-листом `07-app-shell.md` §9.
- Автозаполнение iOS (пароли, «Надёжный пароль») ломает прокрутку: после заполнения обоих полей снимай фокус (см. `Login.svelte`/`Register.svelte`). Не вызывай `setSelectionRange` без нужды: iOS прокручивает страницу к полю.
- Блокировка входа живёт на телефоне (`src/domain/lockout.ts`), настоящая защита от подбора появится на бэкенде. Тестовый аккаунт **admin / admin** засеян в мок (`src/api/mock/seed.ts`), перед бэкендом удалить.
- Бизнес-правила только в `src/domain` (чистые функции + таблица сценариев в тестах); данные только через `src/api` (интерфейс). Экран не ходит в `localStorage` напрямую.
- Граница суток **04:00**, пояс по умолчанию `Europe/Minsk` (решение владельца).
- Эмуляция (Playwright) не воспроизводит клавиатуру, автозаполнение, safe-area, плавность. Всё это пиши как «не проверено на устройстве» и перечисляй, что именно смотреть владельцу.
- Ветка: работай в ветке, которую задаёт среда (часто `claude/...`), если не сказано иное; в отчёте назови её. Не создавай PR, в `main` не пушь.

## Экономия токенов (важно)
Читай только нужные диапазоны файлов; логи вставляй только когда реально нужно; не пересказывай шаги; отвечай коротко по-русски: результат, что осталось неясным, что нельзя проверить без телефона. Файлы кода держи небольшими (до ~300 строк), по одному модулю на ответственность.
