# Архитектура фронтенда — "Энергоська"

> Документ описывает структуру проекта, принципы модульности/переиспользования и систему теминга. Работает в связке с `design-system.md` (соседний файл) — тот является живым, постоянно расширяемым каталогом конкретных стилей и компонентов, который ИИ-агент обязан использовать как источник правды вместо изобретения новых стилей на лету.

---

## 0. Главное правило работы со стилями

**Перед созданием любого нового визуального элемента — сначала ищем в `design-system.md`, есть ли уже подходящий токен/компонент/паттерн.** Если есть — переиспользуем. Если нет, но элемент достаточно универсален, чтобы встретиться ещё раз — создаём его как переиспользуемый примитив/паттерн и **обязательно дописываем запись в `design-system.md`** по шаблону из раздела "Как расширять каталог" того файла. Одноразовые, узкоспецифичные для одного экрана правки — не обязаны попадать в каталог, но такие случаи должны быть редкими: если что-то похожее уже встречалось на другом экране — это уже не одноразовый случай, а кандидат в переиспользуемый паттерн.

Цель: спустя полгода разработки стилевая система не должна превратиться в свалку из полутора сотен несовместимых оттенков "почти одинакового" серого — новый компонент почти всегда должен собираться из уже существующих токенов.

### Принцип трёх слоёв компонентов
1. **primitives/** — не знают о продукте вообще. `Button` не знает, что такое "энергетик". Максимальная переиспользуемость, максимальное тестовое покрытие, минимальные изменения со временем.
2. **composite/** — знают об общих паттернах интерфейса (например, `DualValueDisplay` знает о концепции "два значения от двух людей", но не знает, что это может быть оценка энергетика, а не что-то ещё).
3. **features/…/components** — знают о конкретной предметной области ("DrinkCard", "PriceHistoryChart").

Правило: **компонент никогда не должен "прыгать вниз" по слоям** — `primitives` не импортирует ничего из `composite` или `features`. Импорты идут только "сверху вниз" (features → composite → primitives).

## 2. Система теминга (светлая/тёмная + кастомный акцент)

### 2.1 Механизм
Вся тема выражается через **CSS Custom Properties**, переключаемые атрибутами на корневом `<html>`:

```html
<html data-theme="dark" data-accent="dusty-denim">
```

```css
/* tokens/colors.css — семантические переменные, ссылающиеся на themes/*.css */
:root {
  --color-bg: var(--theme-bg);
  --color-surface: var(--theme-surface);
  --color-text: var(--theme-text);
  --color-accent: var(--accent-current);
  --color-identity-a: #14C7C2; /* Charge — не зависит от темы */
  --color-identity-b: #FF5C7A; /* Pulse — не зависит от темы */
}

[data-theme="dark"] {
  --theme-bg: #121214;
  --theme-surface: #1C1C20;
  --theme-text: #F0F0F2;
  --theme-border: #2A2A30;
}

[data-theme="light"] {
  --theme-bg: #F3F4F7;
  --theme-surface: #FFFFFF;
  --theme-text: #16171B;
  --theme-border: #E2E4E9;
}

[data-accent="dusty-denim"] { --accent-current: var(--accent-dusty-denim); }
[data-accent="ash-sage"]    { --accent-current: var(--accent-ash-sage); }
/* ...остальные варианты, значения — см. design-system.md, раздел "Акцентные цвета" */
```

**Важно**: компоненты **никогда** не обращаются к сырым hex-значениям и никогда не читают `data-theme`/`data-accent` напрямую в JS для выбора цвета. Компоненты используют только семантические переменные (`--color-bg`, `--color-text`, `--color-accent`, `--color-identity-a/b`). Это единственный способ гарантировать, что смена темы/акцента работает мгновенно и без точечных правок в компонентах.

### 2.2 `ThemeProvider`
- Хранит выбор пользователя (`light` / `dark` / `system`) и выбранный акцент (свой для каждой темы — то есть у пользователя фактически хранится пара `{lightAccent, darkAccent}`).
- При `system` — подписывается на `window.matchMedia('(prefers-color-scheme: dark)')` и переключает `data-theme` реактивно.
- Значения синхронизируются с бэкендом (профиль пользователя) и кэшируются в памяти на время сессии (не через `localStorage` — см. ограничение ниже).
- Установка атрибутов на `<html>` — единственная точка мутации DOM для темы, никаких инлайн-стилей на компонентах.

### 2.3 Identity-цвета (Charge/Pulse) — отдельное правило
`--color-identity-a` и `--color-identity-b` **не участвуют** в переключении темы и не зависят от выбора акцента — это единственные два цвета в системе, которые всегда одинаковы, потому что они несут смысловую нагрузку "это данные Вовы / это данные Даши" по всему приложению (числа оценок, обводка аватара, цвет заметки на доске, легенда графиков). Смешивать роль identity-цветов с ролью акцентного цвета запрещено — акцент не должен случайно совпадать с одним из identity-цветов (проверка на достаточный цветовой контраст между акцентными вариантами и identity-цветами — обязательна на этапе добавления нового акцента в палитру).

## 3. Управление состоянием и данными

- **Серверное состояние** — исключительно через React Query (см. tech-spec.md). Каждая feature-папка содержит свой `api.ts` с чистыми функциями запросов и `hooks.ts` с обёртками `useQuery`/`useMutation`.
- **Локальное UI-состояние** (открыта ли модалка, значение слайдера во время перетаскивания до сохранения) — обычный `useState`/`useReducer`, не выносится в глобальные стореы без необходимости.
- Глобальный клиентский стор (Zustand или Context) — только для по-настоящему сквозных вещей: текущая тема/акцент, текущий авторизованный пользователь, состояние "онлайн/оффлайн". Не создавать глобальный стор "на всякий случай" для данных, которые и так живут в React Query.

## 4. Модульность и переиспользование — конкретные правила

1. **Ни одного захардкоженного цвета/отступа/радиуса в компонентах.** Всё — через CSS-переменные из `styles/tokens`. Ревью-чеклист: если в диффе появился `#` (hex) или "магическое" число пикселей вне `tokens/*.css` — это повод остановиться и свериться с каталогом.
2. **Дуальные виджеты — один компонент, не два.** Раз в приложении почти каждый показатель дуален (оценка, счётчики, доска), это должно быть решено **одним** переиспользуемым компонентом `<DualValueDisplay primary={...} secondary={...} />`, а не копипастой JSX с двумя `<span>` на каждом экране, где это нужно.
3. **Форма ввода оценки — один источник правды.** Слайдер с "меткой предыдущего значения" (см. tech-spec.md, 5.5) реализуется один раз как `<RatingSlider />` в `composite/` и переиспользуется и в модалке "Выпить", и в любых будущих местах, где потребуется похожий ввод.
4. **Цветовой пикер тегов/брендов/магазинов — один компонент** `<ColorPicker />`, переиспользуемый везде, где сущность имеет `accent_color` (бренд, магазин, тег).
5. **Пустые состояния и ошибки — единый паттерн**, не придумывается заново на каждом экране (см. `design-system.md`, раздел "Пустые состояния").
6. Каждый компонент в `composite/` и `primitives/` — со своей Storybook-историей (или минимум с примером использования в комментарии наверху файла), чтобы агент, ищущий "чем нарисовать бейдж", находил готовый пример, а не писал JSX заново.

## 5. Соглашения по именованию и структуре файлов

- Компоненты — `PascalCase.tsx`, один компонент = один файл (плюс опционально `.module.css` рядом, если стиль специфичен и не покрывается токенами напрямую).
- Хуки — `useCamelCase.ts`.
- Файлы стилей — `kebab-case.css`.
- Каждая feature-папка не импортирует внутренности другой feature-папки напрямую (`features/drinks` не должен тянуть компонент из `features/shops/components/*`) — если нужен переиспользуемый кусок между фичами, он поднимается на уровень `composite/`.

## 6. Производительность на уровне архитектуры компонентов

- Тяжёлые страницы (`DrinksListPage`, `StatsPage`) — `React.lazy` + маршрутный сплиттинг.
- `DrinkCard` в списке — обёрнут в `React.memo`, пропсы — примитивы/стабильные ссылки (не создавать новые объекты/функции инлайн в `.map()` при рендере списка).
- Слайдер оценки — как описано в tech-spec.md, позиция акцентной метки предыдущего значения обновляется напрямую через `ref`/CSS custom property, а не через `setState` на каждое движение пальца.
- Графики (recharts) — рендерятся лениво (по клику "раскрыть график"), не сразу при рендере карточки.
