# Энергоська — исчерпывающая спецификация продукта

> Документ предназначен для ИИ-агентов, которые будут проектировать и реализовывать приложение. Описывает функционал, поведение, модель данных, API верхнего уровня и архитектурные решения. Приложение — PWA для двух пользователей (пара), с "взрослой" расширяемой архитектурой.

---

## 0. Суть продукта

Приложение для коллекционирования, оценки и ранжирования энергетических напитков двумя пользователями (парой). Каждый напиток ("энергетик") имеет карточку с фото, брендом, вкусовыми тегами, признаком "с сахаром/без сахара", КБЖУ, ценой в двух валютах и историей дегустаций ("питьё"). Оценка везде **дуальна**: у каждого показателя одновременно отображается значение обоих партнёров. Общий пул сущностей (бренды, магазины, теги, сами энергетики) редактируется любым из пользователей без ограничений прав — приложение работает как общее "хозяйство" пары.

Стек: **FastAPI** (backend) + **React** (frontend, PWA) + реляционная СУБД (рекомендация — PostgreSQL). Отдельный **Go-микросервис** для очереди обработки фото (удаление фона, модель BiRefNet_HR), работающий по pull-модели с домашнего компьютера пользователя.

Критический нефункциональный приоритет: **корректная PWA под iOS Safari** — установка на домашний экран, Web Push, нативные жесты/анимации, безопасные зоны (safe-area-inset), поведение как у "настоящего" приложения. Адаптивность: iPhone, iPad, десктоп.

## 1. Пользователи, аутентификация, партнёрство

### 1.1 Модель пользователя
- Полноценная таблица `users`, не захардкоженные два юзера — расчёт на будущее расширение.
- Поля: `id`, `login` (уникальный, используется для входа, **неизменяемый**), `nickname` (отображаемое имя, изменяемое, участвует в поиске наравне с login), `password_hash` (argon2 или bcrypt), `avatar_url`, `country` (enum: `BY` / `RU`, влияет на дефолтную валюту), `theme` (`light` / `dark` / `system`), `accent_color`, `status_title` (текстовое звание, MVP-значение по умолчанию — "Энергетикоголик", в будущем будет проставляться ML-агентом раз в неделю; на MVP — статичное неизменяемое юзером поле), `created_at`.
- Регистрация: примитивная форма — `login` + `password` + подтверждение пароля. Без email, без верификации.
- Восстановление пароля: **не реализуется на MVP**. Предполагается ручное вмешательство второго пользователя/администратора БД.
- Сессии: долгоживущие (максимальный комфорт — "не разлогиниваться месяцами"). Рекомендация: JWT access-токен (короткий TTL) + refresh-токен с длинным TTL (месяцы), хранящийся в httpOnly cookie, с тихим автообновлением на фронте.

### 1.2 Онбординг после регистрации
1. Выбор страны (Беларусь/Россия) → определяет дефолтную валюту ввода цены.
2. Загрузка аватара с кропом под круг (WYSIWYG-кроп на фронте, пользователь сам двигает/масштабирует изображение перед сохранением). Шаг можно пропустить — используется дефолтная заглушка.

### 1.3 Партнёрство
- Отдельная сущность `partnerships`: `id`, `user_a_id`, `user_b_id`, `status` (`pending`, `accepted`), `initiated_by`, `created_at`, `accepted_at`.
- Реализовано как m2m-связь на уровне БД (архитектурный задел на будущее — множественные партнёрства), но **бизнес-логика MVP жёстко ограничивает**: у пользователя может быть не более одного активного (`accepted`) партнёрства и не более одного исходящего `pending`-приглашения одновременно.
- Флоу: пользователь A вводит nickname/login пользователя B в настройках → создаётся запись `pending` → пользователю B приходит **Web Push уведомление** → на экране настроек B видит входящий запрос с кнопками "Принять"/"Отклонить" → при принятии статус переходит в `accepted`, приглашения с обеих сторон блокируются.
- Разрыв партнёрства: доступен только через явное удаление, с модальным окном подтверждения. После разрыва — **мягко**: собственные данные (лог питья, оценки) каждого пользователя остаются как личные, просто перестают агрегироваться "дуально". История не удаляется, аудит разрыва не ведётся.
- Пуш-уведомления (MVP, только эти три триггера):
  1. Входящий запрос на партнёрство.
  2. Партнёр только что выпил энергетик (с оценкой).
  3. Фото энергетика обработалось (фон удалён), карточка готова.

## 2. Модель данных: основные сущности

### 2.1 Общий принцип
Бренды, магазины, теги и сами энергетики образуют **общий редактируемый пул** — создавать и редактировать их может любой авторизованный пользователь без ограничений. Аудита изменений (кто/когда переименовал) на MVP **нет**. Удаление везде **мягкое** (soft-delete / архивация, поле `is_archived`), кроме случая каскада бренда (см. ниже). Архивные объекты по умолчанию скрыты из выборок, но не физически удаляются.

### 2.2 Бренд (`brands`)
- Поля: `id`, `name` (уникальное, обязательное), `accent_color`, `is_archived`, `created_at`.
- **Без логотипа и описания** — сознательное решение, бренд это только имя (+ акцентный цвет для визуального оформления).
- Обязателен для энергетика: у энергетика всегда должен быть привязан бренд.
- **Каскад удаления**: архивация бренда архивирует все привязанные к нему энергетики (с явным предупреждением в модалке подтверждения).
- Создание — inline при добавлении энергетика, интерфейс заточен под **выбор из существующего списка** (searchable select/autocomplete), а не под ввод текста с нуля каждый раз. Полноценный CRUD (переименование, смена цвета, архивация) вынесен в Настройки → "Работа с записями" → "Бренды".
- Отдельная **страница бренда**: список всех энергетиков этого бренда, средняя дуальная оценка по бренду, суммарное количество "выпитого" под этим брендом (я/партнёр/общее), CRUD-действия тут же на странице.

### 2.3 Магазин (`shops`)
- Поля: `id`, `name` (обязательное), `logo_url` (круглое лого, кроп под круг на фронте при загрузке — аналогично аватару), `accent_color`, `is_archived`, `created_at`.
- **Необязателен** для энергетика/записи о питье. Без адреса и геолокации — это скорее "сеть" (например, "Пятёрочка", "Соседи"), а не конкретная точка.
- Архивация магазина **не влияет** на связанные энергетики.
- Создание — inline при отметке "выпил" (searchable select/create), полноценное редактирование (смена фото, цвета) доступно из карточки магазина или Настроек.
- Отдельная **страница магазина ("витрина")**: список энергетиков, которые покупались в этом магазине; переключатель графика цены — "тренд по этому магазину" / "общий тренд по всем магазинам".

### 2.4 Тег (`tags`)
- Поля: `id`, `name`, `type` (enum: `flavor` / `brand` — на будущее, но по факту на MVP используется только `flavor`, т.к. бренд — отдельная сущность), `accent_color`, `created_at`.
- Плоская структура, **без иерархии** и без группировки (никаких "основной вкус" / "дополнительный вкус" — намеренное упрощение).
- Энергетик может иметь произвольное количество тегов (например, "Горилла Манго Кокос" → теги `манго`, `кокос`).
- Создание — inline при добавлении энергетика, с упором на выбор из существующих (autocomplete), полноценный CRUD — в Настройках.
- У каждого тега — цветовой пикер (нативный, эппловский стиль). В настройках приложения предусмотреть опцию "монохромный режим" — глобально отключает цветные бейджики в пользу единого нейтрального стиля.

### 2.5 Абсолют (признак "с сахаром / без сахара")
- **Важно**: это НЕ тег. Отдельное обязательное поле у энергетика — `sugar_type` (enum: `sugar` / `sugar_free`), одиночный выбор (radio), обязателен при создании энергетика. Технически и логически отделён от системы тегов, участвует в фильтрах как отдельная ось.

### 2.6 Энергетик (`energy_drinks`)
- Поля: `id`, `name`, `brand_id` (FK, обязательное), `sugar_type` (enum, обязательное), `photo_url` (обязательное поле, но допускает промежуточное состояние "в обработке"), `photo_status` (enum: `pending`, `processing`, `done`), `description` (текст, редактируемый, необязательный), `calories`, `proteins`, `fats`, `carbs` (КБЖУ — заполняется один раз при создании любым пользователем, далее общее поле для обоих, редактируемое через карточку), `is_favorite_wova` (bool), `is_favorite_dasha` (bool) — или через отдельную таблицу `favorites (user_id, drink_id)` для расширяемости, `is_archived`, `created_at`.
- Связь many-to-many с тегами через промежуточную таблицу `drink_tags`.
- Создание:
  - Быстрое (кнопка "+" на странице списка энергетиков): только бренд, теги, абсолют, КБЖУ, фото — **без оценки**.
  - Через глобальную кнопку "Энергоснулся" (см. п.4): если энергетика ещё нет в базе — можно создать его прямо в процессе, тем же коротким флоу, и сразу продолжить в модалку оценки.

### 2.7 Фото и обработка
- При загрузке фото создаётся `photo_jobs` запись со статусом `pending`.
- Go-микросервис на компьютере пользователя работает по **pull-модели**: когда пользователь запускает локальное приложение, оно опрашивает эндпоинт очереди задач, забирает `pending`-таски, прогоняет через модель `ZhengPeng7/BiRefNet_HR` (удаление фона), отдаёт результат обратно на бэкенд через отдельный API-эндпоинт (например, `POST /photo-jobs/{id}/complete` с готовым файлом/URL).
- Пока `photo_status != done` — карточка показывает плейсхолдер "Фото в обработке".
- По завершении обработки — Web Push пользователю, инициировавшему загрузку ("Фото обработалось, зайди глянь").
- Кнопка "Переснять" — полностью затирает старое фото, создаёт новую `photo_jobs` запись, статус карточки возвращается в `processing`.

### 2.8 Запись о питье (`drink_logs`)
- Поля: `id`, `drink_id` (FK), `user_id` (FK — конкретный пользователь, который пил; лог принадлежит только ему, у энергетика параллельно существуют независимые логи Вовы и Даши), `rating_smell`, `rating_taste`, `rating_aftertaste`, `rating_intensity` (все 0–10, дробные значения допустимы, если UI слайдера это подразумевает), `rating_overall` (**вычисляемое** поле — среднее четырёх параметров, никогда не задаётся вручную), `shop_id` (FK, nullable), `price_byn`, `price_rub` (оба хранятся как отдельные фиксированные числа на момент записи — **не пересчитываются задним числом** при изменении курса), `comment` (текст, необязательный), `created_at`.
- Каждое "питьё" — обязательная процедура с оценкой (осознанное решение: без быстрого "просто отметить как выпил без оценки" — "это должно быть искусство").
- Дефолтные значения слайдеров при открытии модалки — равны последним значениям **этого же пользователя** по этому энергетику (если предыдущая запись существует).

### 2.9 Доска / заметки к энергетику (`drink_notes`)
- Поля: `id`, `drink_id` (FK), `user_id` (FK), `text`, `created_at`.
- Привязана к **конкретному энергетику** (не общая доска приложения).
- Отображение: единая лента, отсортированная по дате ("стена позора"), с визуальным разделением/цветовым кодированием по автору (Вова/Даша). Записи **не редактируются и не удаляются** после создания — только добавление новых.

### 2.10 Курс валют
- Отдельная сущность/кэш `exchange_rates`: `date`, `rate_byn_to_rub` (или наоборот), обновляется автоматическим фоновым job'ом раз в сутки через открытое API курсов валют.
- Fallback-значение, если внешнее API недоступно: **27 российских рублей за 1 белорусский рубль**.
- При вводе цены в модалке "Выпить" — дефолтное поле ввода в валюте страны пользователя (из профиля), с возможностью вручную переключить валюту ввода. При сохранении бэкенд считает и фиксирует оба значения (`price_byn`, `price_rub`) на основе актуального курса на момент записи.

## 3. Фильтры (сквозной механизм)

Используются в списке энергетиков, в рандоме, частично в статистике. Оси фильтрации:
- Бренд (multi-select)
- Вкусовые теги (multi-select)
- Абсолют: с сахаром / без сахара / любой
- Магазин (multi-select)
- Признак "Любимое"
- Диапазон итоговой оценки (слайдер range)
- Диапазон цены (в выбранной валюте)
- Диапазон КБЖУ (как минимум по калориям)
- Диапазон дат (дата добавления энергетика либо дата последнего "питья")
- "Пробовал / не пробовал" (относительно текущего пользователя)
- **3-стейт "Я / Партнёр / Общее"** — определяет, чьи данные (кол-во выпитого, оценки) учитываются при агрегации:
  - "Я" — только записи текущего пользователя.
  - "Партнёр" — только записи партнёра.
  - "Общее" — суммарно/усреднённо по обоим.

Все фильтры комбинируются по **И**-логике (AND).

## 4. Экраны приложения

### 4.1 Логин / Регистрация
Простая форма входа (login + password) и регистрации (login + password + подтверждение). После успешной регистрации — двухшаговый онбординг (страна → аватар), см. п. 1.2.

### 4.2 Главная
- Крупная, самая заметная кнопка **"Энергоснулся 🔥"** — глобальный вызов флоу "выпил" (см. 4.5).
- Лента последних событий на двоих: кто что выпил и с какой оценкой, кто добавил новый энергетик/бренд/тег, в хронологическом порядке.
- Виджет "рандом дня" — превью случайной карточки (с учётом сохранённых фильтров пользователя) и кнопкой перегенерации.
- Краткая сводка активности за неделю/месяц (я / партнёр).
- Быстрый переход к отмеченному "любимому" энергетику.

### 4.3 Список энергетиков
- Сетка карточек: фото, имя, бренд, дуальная итоговая оценка (моя — крупным шрифтом, партнёра — рядом мельче).
- Сворачиваемая панель фильтров (см. раздел 3).
- Сортировки: по оценке, по количеству выпитого, по дате добавления, по алфавиту.
- Плавающая кнопка "+" — быстрое создание "пустой" карточки энергетика (без оценки).

### 4.4 Карточка энергетика
- Фото (либо готовое обработанное, либо плейсхолдер "в обработке" с кнопкой "Переснять").
- Название, бренд (кликабельная ссылка → страница бренда), метка абсолюта, цветные теги-бейджики.
- Итоговая дуальная оценка крупно/мельче + переключаемая иконка "любимое" (сердечко/звезда, тоггл на пользователя).
- Четыре параметра оценки (запах/вкус/послевкусие/ядрёность), отображаются дуально; тап по показателю раскрывает интерактивный график динамики этого параметра по времени (отдельно для каждого пользователя либо наложенно).
- Цена — текущая/последняя в обеих валютах; тап раскрывает интерактивный график цены с переключателем "по всем магазинам" / "по конкретному магазину".
- Блок КБЖУ — редактируемый.
- Описание — редактируемый текст.
- Кнопка **"Выпить!"** — открывает модалку оценки, предзаполненную данными этого энергетика.
- История питья — компактный лог: дата, автор, свёрнутые оценки, магазин, цена, комментарий.
- Доска — лента заметок (см. 2.9), с разделением по автору, сортировка по дате, без редактирования.

### 4.5 Модалка "Выпить" / "Энергоснулся"
- Локальный вызов (с карточки конкретного энергетика) — сразу открывает форму оценки.
- Глобальный вызов (с главной) — сначала поиск/выбор энергетика через тот же интерфейс фильтров, что и в списке, либо кнопка "Создать новый" (короткий флоу создания энергетика "на лету", после которого пользователь сразу попадает в форму оценки).
- Форма оценки:
  - 4 слайдера (0–10): запах, вкус, послевкусие, ядрёность. Дефолт = предыдущий результат **этого же** пользователя по этому энергетику (если есть). На треке слайдера — акцентная метка на месте предыдущего значения + краткая легенда-подсказка ("│ — ваша прошлая оценка").
  - Итоговая оценка — вычисляется на лету как среднее четырёх параметров, отображается для информации, **не редактируется**.
  - Магазин — inline searchable select / создание нового, необязательно.
  - Цена — необязательное поле, дефолтная валюта из профиля страны пользователя, с ручным переключением валюты.
  - Комментарий — необязательное текстовое поле.
  - Кнопка "Сохранить" → создаёт запись `drink_logs`, инкрементирует счётчики, закрывает модалку с подтверждением (toast).

### 4.6 Страница бренда
Имя, акцентный цвет, сетка принадлежащих энергетиков, средняя дуальная оценка по бренду, суммарное количество выпитого (я/партнёр/общее). CRUD прямо на странице: переименовать, сменить цвет, архивировать (с явным предупреждением о каскадной архивации всех энергетиков бренда).

### 4.7 Страница магазина
Имя, круглое лого, акцентный цвет. "Витрина" — список энергетиков, которые здесь покупались, с переключателем графика цен (тренд по этому магазину / общий тренд). CRUD: смена фото/имени/цвета, архивация (без влияния на энергетики).

### 4.8 Статистика (отдельная вкладка навигации)
- Переключатель "Я / Партнёр / Общее" (тот же 3-стейт).
- Карточки-метрики: всего выпито, потрачено (в обеих валютах), средняя оценка, самый частый бренд, самый частый магазин, самая долгая "серия без энергетика".
- График активности по времени (гистограмма количества "питья" по дням/неделям/месяцам, с переключением гранулярности).
- Топ-5 брендов и топ-5 энергетиков (по оценке и отдельно по количеству выпитого).
- **Радар-диаграмма вкусового профиля** (средние значения по 4 параметрам): по умолчанию один усреднённый контур согласно выбранному 3-стейту; отдельный тумблер "Сравнить с партнёром" — накладывает второй контур для визуального сравнения.
- Динамика среднего чека (цены) по времени.

### 4.9 Настройки
- Профиль: аватар (смена с кропом), никнейм (редактируемый), логин (только отображение, неизменяем), страна/дефолтная валюта.
- Партнёрство: поле приглашения по нику/логину → статус "ожидание ответа"; если есть входящий запрос — карточка с кнопками принять/отклонить; если партнёр уже есть — его карточка + кнопка "Удалить партнёра" (с модалкой подтверждения).
- Внешний вид: переключатель темы (light / dark / system), выбор акцентного цвета (5–6 приглушённых вариантов, набор свой для каждой темы), опция "монохромные теги".
- Звание/статус — отображение текущего статуса (нередактируемо пользователем, зарезервировано под будущий ML-функционал).
- "Работа с записями": разделы Бренды / Магазины / Теги — списки с возможностью переименования, смены цвета, архивации/разархивации.
- Уведомления: кнопка запроса разрешения на Web Push.
- Выход из аккаунта.

### 4.10 Экран "нет интернета"
Оффлайн-режим не поддерживается. При потере соединения — простой информационный экран с просьбой подключиться к интернету (без кэша данных).

## 5. Архитектурные рекомендации

### 5.1 Backend
- **FastAPI** + **PostgreSQL** (реляционная модель хорошо ложится на описанные сущности и их связи; JSON-поля не нужны, все данные строго структурированы).
- ORM: SQLAlchemy 2.x + Alembic для миграций (важно, учитывая "максимально долгое хранение" и развитие схемы во времени).
- Аутентификация: JWT access-токен (короткий TTL, ~15 мин) + refresh-токен в httpOnly secure cookie с длинным TTL (например, 90–180 дней, скользящее продление при активности).
- Пароли — argon2id.
- Структура API — REST-ресурсы: `/auth`, `/users/me`, `/partnerships`, `/brands`, `/shops`, `/tags`, `/drinks`, `/drinks/{id}/logs`, `/drinks/{id}/notes`, `/photo-jobs`, `/exchange-rates`, `/stats`.
- Web Push: хранение push-подписок пользователя (`push_subscriptions` таблица), отправка через `pywebpush` или аналог, три триггера см. п. 1.3.
- Фоновые задачи: планировщик (APScheduler или Celery beat) для (а) ежедневного обновления курса валют, (б) в будущем — еженедельного ML-агента статусов. Использование полноценной очереди (Celery + Redis) оправдано, если проект будет расти; для текущего масштаба (2 пользователя) достаточно APScheduler internal jobs.
- **Очередь фото-задач**: простая таблица `photo_jobs` (status: pending/processing/done/failed) + два эндпоинта: `GET /photo-jobs/next` (Go-воркер забирает задачу, помечает `processing`) и `POST /photo-jobs/{id}/complete` (воркер отдаёт результат, бэкенд помечает `done`, обновляет `photo_url` энергетика, шлёт push). Аутентификация воркера — отдельный статический API-ключ/токен сервиса (не пользовательский JWT).

### 5.2 Frontend
- **React** + TypeScript, PWA (service worker для установки на домашний экран и push-подписки; кэш ассетов, но без оффлайн-данных согласно решению не поддерживать оффлайн).
- Роутинг: React Router.
- Состояние сервера: React Query (TanStack Query) — удобно для инвалидации при дуальных обновлениях (партнёр что-то изменил).
- Графики: recharts или аналог, лёгкая интерактивность (тап → раскрытие).
- Цветовые пикеры — нативный `<input type="color">` либо кастомный компонент в стиле iOS color picker.
- Кроп изображений (аватар, лого магазина) — на фронте (например, react-easy-crop), отправка на бэкенд уже обрезанного изображения.

### 5.3 PWA / Safari-специфика (критический приоритет)
- Полный `manifest.json` (icons всех размеров, `display: standalone`, `theme_color`, `background_color`).
- `apple-touch-icon`, `apple-mobile-web-app-capable`, `apple-mobile-web-app-status-bar-style` мета-теги для корректного вида при добавлении на домашний экран.
- Учёт safe-area-inset (вырез/notch, home-indicator) через CSS `env(safe-area-inset-*)`.
- Web Push на iOS работает **только** для PWA, установленных на домашний экран (с iOS 16.4+) — это ограничение уже учтено (пользователи устанавливают приложение руками, fallback не нужен, т.к. заранее оговорено, что оба пользователя это сделают).
- Нативные жесты/анимации: избегать резиновой прокрутки не в тех местах, использовать плавные transition при переходах между экранами, приближенные к системным (например, через Framer Motion), тактильный фидбек не поддерживается веб-платформой — не закладывать.
- Тестирование строго через "Добавить на экран Домой" в Safari, а не через обычный браузер-таб.

### 5.4 Ключевые архитектурные решения — сводка
| Решение | Обоснование |
|---|---|
| Полноценная таблица `users` вместо захардкоженных двух профилей | Явное требование "взрослой" расширяемой архитектуры |
| Партнёрство как m2m-таблица с бизнес-ограничением "макс. 1 активный" | Задел на будущее без усложнения MVP |
| Общий редактируемый пул сущностей без прав/ролей | Осознанное упрощение — приложение для доверенной пары |
| Soft-delete/архивация везде, кроме каскада бренда | Соответствует принципу "почти ничего не удаляется" |
| Цена хранится как два зафиксированных числа (BYN и RUB), а не "база + курс" | История цен не должна "переоцениваться" задним числом при изменении курса |
| Итоговая оценка — вычисляемое поле, не редактируется вручную | Явное требование ("математическое подтверждение") |
| Очередь фото-задач как pull-модель через API, а не push на воркер | Воркер живёт на домашнем компьютере, не имеет статического адреса/аптайма |
| Логин ≠ никнейм | Явное разделение идентификатора входа и отображаемого/искомого имени |

## 6. Открытые вопросы / решения "на усмотрение агента-разработчика"
Ниже — моменты, которые не были жёстко зафиксированы в обсуждении и оставлены на техническое усмотрение при реализации (в рамках уже описанных принципов):
- Точный формат хранения дробных значений слайдеров оценки (шаг 0.1 или 0.5) — рекомендация: шаг 0.5 для баланса выразительности и удобства UI.
- Конкретный open API для курса валют — любой стабильный бесплатный источник с ежедневным обновлением (например, exchangerate.host или аналог), с обязательным fallback-константой (27 RUB за 1 BYN) при недоступности.
- Иконки для тегов (помимо цвета) — не оговаривались, можно не делать на MVP, оставить только цветной бейдж с текстом.
